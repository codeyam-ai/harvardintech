### What the ~170 test pages are (plain answer)

They are **not the CMS.** They are screenshot pages for the project tooling (codeyam). Each one renders a single component, such as a board tile, a donor card or a deploy banner, in one fixed state, so the tool can photograph it. There are 81 standalone pages plus 89 generated by one route file, `src/pages/isolated-components/[name].astro`: 170 in total. The tool only ever needs them on the local dev server. Today they ship with every deployed build, and they are not behind the passphrase.

Some of them show sample bios under real board names (Ben Wei, Peter Boyce, Krysia Lenzo, Jessica Li, Nadia Eldeib). These come from `BOARD_BIOS` in `[name].astro`, `BoardMemberTile.astro` and `BoardMemberTile-Initials.astro`. On a public build, all 170 pages would also land in `sitemap.xml`.

## Recommendations

### A. Search and share links (PAGES_SITE)
- **Option 1:** set `PAGES_SITE` to `https://codeyam-ai.github.io`. This fixes the dead address, but share cards would still advertise the preview.
- **Option 2:** set `PAGES_SITE` to `https://harvardintech.com` today. This breaks the links, because `/harvardintech` stays in every canonical URL.
- **Option 3 (pick):** add a separate `CANONICAL_ORIGIN` setting, `https://harvardintech.com`. Canonical links, share cards, structured data, `llms.txt` and the sitemap line in robots.txt are built from it, with the base path removed. `PAGES_SITE` becomes `https://codeyam-ai.github.io`, because that is where the preview really is.

  Why: this matches the owner's note exactly. Every advertised URL names the live site, and the preview stays `noindex` plus `Disallow: /`. At launch the two values meet, and `CANONICAL_ORIGIN` can fall back to `site`.

### B. The preview password
The password is effectively public. It sits in plain text in `src/lib/previewGate.ts` (as the default), `public/review/index.html:473`, `public/donor-network.html:1892`, `docs/nicole-review.md` and `DEPLOY_SETUP.md:189`. It is also in git history, so it has to be changed, not just hidden.

- **Option 1 (pick):** change the password and keep it only in a secret. Store it as a GitHub Actions secret, `PREVIEW_GATE_PASSPHRASE`. Remove the default from the code, so a gated build without the secret fails. Commit a placeholder in the two static files and fill it in at build time. Remove it from every doc, and share it only through a password manager.

  Why: cheap, and it closes every place the password leaks from the repo. It is still a deterrent, not real protection: anyone who can load the page can read the check in its source. That is proportionate for content that goes public at launch anyway.
- **Option 2:** real server-side access control, such as Cloudflare Access or a password-protected Netlify or Cloudflare Pages host in front of the preview. This is genuinely private but means new hosting and accounts. Worth it for the launch-day private editor site if the team wants real locks. That can be decided then.
- **Option 3:** encrypt each page's content with the password (the approach the editor already uses for password-protected previews). Strong, but it breaks assets and search across a whole site. Overkill here.

### C. Keeping internal files off the public site
- **Option 1:** hand-migrate the test pages elsewhere. Rejected. The tooling's isolation-route migration has no Astro path.
- **Option 2:** a `getStaticPaths` guard plus a sitemap filter. This only reaches the 89 generated pages. The 81 standalone pages and the raw `public/` files have no `getStaticPaths`.
- **Option 3 (pick):** a small build step removes a named list of internal paths from `dist/` on the public build, plus a sitemap filter for the same list, plus the `getStaticPaths` guard in `[name].astro`.

  Why: one list in `src/lib/publishTrack.ts` covers the test pages and the `public/` files alike, and it is unit-testable. It follows the pattern the cutover runbook already uses (`includeCutoverRunbook`). The tooling keeps working, because it captures against `astro dev`.
